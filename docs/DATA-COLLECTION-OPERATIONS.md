## 1. 현재 운영 정책

**정기 수집 → 원문 검증 → 연결 인덱스 검증 → 단일 데이터 커밋 → GitHub Pages 배포 요청까지 자동으로 처리한다. 사용자가 매번 실행하거나 운영 반영할 필요가 없다.**

일정은 `config/collection-schedules.json`과 단일 예약 워크플로 `.github/workflows/sync-food-data.yml`에서 관리한다. 예전 수동 워크플로의 예약은 제거하여 중복 수집하지 않는다. C005는 갱신 중단 자료이므로 기존 검증본을 보존한다.

## 4. 자동 처리 순서와 정상본 보존

| 단계 | 자동 처리 | 실패 시 처리 |
| --- | --- | --- |
| 예약·실행 선택 | 5개 cron과 실행 모드를 매핑. 자동 작업은 동일 동시 실행 그룹으로 순차 처리 | 알 수 없는 모드·일정은 실행하지 않음 |
| 격리 수집 | 운영 파일을 수정하지 않는 임시 세대에서 전체 수집. 공식 원문·상태·분할 파일 생성 | 실패한 서비스의 기존 원문·원본 파일 보존 |
| 전수 검증 | 행 수·고유 행·원본 필드·파일 크기·SHA-256·식품/레시피 코드 확인 | 이전 정상본의 50% 미만으로 줄면 반영 보류. 빈 응답으로 기존 자료 제거하지 않음 |
| 연결 갱신 | 변한 소스의 검색 인덱스와 번호 포인터 갱신, 전체 포인터·해시 검증 | 원문과 인덱스를 함께 검증하기 전 운영 파일 교체하지 않음 |
| 세대 교체 | 검증된 파일 묶음만 교체. 로컬 교체 중 오류 발생 시 전체 묶음 복구 | 원문만 새 버전이고 인덱스는 이전 버전인 상태를 커밋하지 않음 |
| 상태 기록 | 최근 수집·검증 결과, 실패 서비스, 마지막 성공, 실행 링크 기록 | 실패해도 마지막 정상 데이터와 실제 실패 상태를 함께 표시 |
| 운영 반영 | 데이터 파일만 한 커밋으로 main에 반영. 최신 코드 변경을 rebase하여 보존 | 데이터 충돌 시 중단하며 강제 덮어쓰기하지 않음 |
| 배포 확인 | 기존 main 루트 Pages 빌드를 REST API로 명시 요청하고 대상 커밋의 빌드 성공 확인 | 배포 오류·시간 초과를 작업 실패로 표시 |

추가 API 일부가 실패하면 해당 서비스의 정상본을 유지하고, 나머지 검증된 자료 및 실패 상태를 함께 반영한다. 이후 작업은 실패 상태로 종료하여 성공으로 숨기지 않는다. 레시피·영양 그룹은 관련 파일·연결 검증이 모두 성공한 세대만 반영한다.

GitHub 공식 문서에 따라 `GITHUB_TOKEN`으로 커밋·푸시한 것만으로 Pages 빌드가 시작된다고 가정하지 않는다. `pages: write` 권한으로 기존 Pages 빌드를 명시 요청하며 별도의 경쟁 배포 경로를 추가하지 않는다.

## 5. 회수·판매중지의 최신성

| 상황 | 자동 처리 |
| --- | --- |
| 정상 실시간 API | 시간별로 전체 API 행을 조회하고 참조 총건수와 일치하는지 확인 |
| API 페이지의 총건수 불일치·일시 오류 | 재시도 후 공식 전체파일 수집·검증으로 대체 가능 |
| 전체파일 대체 성공 | `apiPageAttemptStatus`, 사유, 전체파일 기준 및 최신성 제한을 표시하고 작업 결과를 주의 상태로 기록 |
| API·전체파일 모두 실패 | 기존 정상 회수 수집본을 보존하고 갱신 실패 표시 |
| 비정상적으로 큰 회수 데이터 | 실시간 전체 페이지 조회는 10,000건 이하로 제한하여 무제한 호출을 방지 |
| 공고 연결 | 품목번호가 같아도 제조일·소비기한·대상 범위를 확인. 공고가 없다고 안전을 보증하지 않음 |

기준 수집본에서는 I0490 파일 378행/API 379건, I0580 파일 39,422행/API 39,406건, I1250 파일 1,080,827행/API 1,081,077건의 차이가 있었다. 차이는 상태 JSON과 화면에 각각 기록하며 실시간 API와 동일한 스냅샷이라고 표시하지 않는다. C005의 기준 원문 259,793행 중 고유 행은 259,741개이고 중복 52행도 보존했다.

## 6. 데이터 성격에 맞는 연결 기준

| 관계 | 기준 | 제한 |
| --- | --- | --- |
| 레시피 → 음식 영양 | 음식명·허용 별칭·가장 구체적인 이름 포함 후보 | 해당 레시피의 영양값으로 확정·합산하지 않음 |
| 영양 제품 → I1250·C002·I0490·과거 C005 | 정확히 같은 품목제조보고번호 | 제품명만으로 같은 제품·함유 원료·안전 여부 확정하지 않음 |
| I1250 → I0580 | 정확히 같은 업소 인허가번호 | 업소 자료이며 개별 제품의 현재 HACCP 인증 보장 아님 |
| 레시피 재료 → I1020·I2520 | 공식 이름·이명 일치 후보 | 사용 부위·가공·조건을 함께 확인. I1020에 원료코드가 있다고 가정하지 않음 |
| 바코드 → C005 | 과거 바코드 정확 일치 | 현재 유통 제품·진위·재고의 확인 자료 아님 |

알레르기 성분·교차 접촉은 실제 제품 표시와 원문을 확인한다. 음식·가공식품·건강기능식품과 원료·업소·회수 공고를 같은 종류의 자료로 합치지 않는다.

## 7. 운영 확인과 수동 복구

일상 운영에서 사용자가 할 일은 [수집·자동화 현황](https://softm.github.io/foodhannun/data-status.html)의 최근 결과를 확인하는 것이다. 정기 갱신은 자동이며, 아래 실행 버튼은 즉시 갱신이나 장애 복구가 필요할 때만 쓴다.

[자동 수집 워크플로](https://github.com/softm/foodhannun/actions/workflows/sync-food-data.yml) → **Run workflow → main → mode 선택**으로 실행하면 수집부터 배포까지 동일하게 처리한다.

| mode | 실행 범위 | 반영 |
| --- | --- | --- |
| recalls | 회수·판매중지 | 자동 검증·반영·배포 |
| daily | I1250·C002·I0580 | 자동 검증·반영·배포 |
| weekly | I1020·I2520 | 자동 검증·반영·배포 |
| recipes | COOKRCP01 레시피 | 자동 검증·연결 갱신·반영·배포 |
| nutrition | 음식·가공식품·건강기능식품 영양 3종 | 자동 검증·연결 갱신·반영·배포 |
| official-all | 갱신 가능한 공식 API 6종 전체 | C005 제외, 자동 검증·반영·배포 |

기존 `collect-additional-data.yml`은 원본 재변환·격리 브랜치 복구 도구이고 `collect-nutrition.yml`은 보관 전용 도구다. 정기 운영이나 일반적인 즉시 갱신에는 위 통합 워크플로를 사용한다. 원본 재변환의 `reuse_source=true`는 새 수집이 아니며 현재 `source-original.gz`가 있는 서비스에만 사용한다. 기존 C005는 JSONL 보존본이고 재변환용 원본 gzip이 없어 해당 옵션에서 제외한다.

| `scripts/publish-food-data.py` | 데이터만 커밋·동시 변경 보존·Pages 명시 배포 요청과 빌드 확인 |
| `data/collection-runs.json` | 그룹별 최근 시도, 마지막 성공, 실패·대체 여부, 실행 링크 |
| `data/collection-status.json`, `data-status.html` | 실제 수집본·건수·시각·차이와 자동화 현황 |
| `data/collection/{서비스}/` | 상태·공식 원본·10,000행 단위 gzip JSONL |
| `data/nutrition/` | 영양 원본 열 보존과 1,000행 분할 gzip JSON |
| `data/food-safety/` | 검색 인덱스와 256개 번호·원료명 조회 버킷 |
| `data/food-links.json.gz` | 레시피·음식 영양 후보와 근거 |
| `FOODSAFETY_API_KEY` | 기존 GitHub Actions Secret. 브라우저·HTML·문서에 값 저장 금지 |
| `contents: write`, `pages: write` | 검증 데이터 커밋 및 기존 Pages 빌드 요청 권한 |

변하지 않은 원문의 검색 인덱스를 재사용하고 변한 소스의 포인터만 재생성한다. 재사용 인덱스도 해시·범위·총건수를 검증한다. 장애 진단 상태 결과물은 30일 보관하며, 정상 운영 데이터는 Git 이력에 남는다. 추가 API의 인증 확인·조회는 순차 실행하고 일시 오류는 최대 7회 시도한다. 일반 앱 검색은 공공 API 인증키를 사용하지 않는다.
