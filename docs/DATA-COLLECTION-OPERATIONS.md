## 1. 현재 운영 상태

**레시피만 매일 수집·검증 후 운영에 자동 반영한다. 영양 DB는 주간 수집 후 보관하며, 추가 7개 API는 현재 수동 수집이다.**

| 구분 | 현재 설정된 수집 주기(KST) | 수집 후 처리 | 운영 사이트 자동 반영 |
| --- | --- | --- | --- |
| 레시피 COOKRCP01 | 매일 **06:20** · 수동 실행 가능 | 전체 수집 → 검증 → 음식 영양 연결·수집 현황 재생성 → main commit/push | **예**. main 변경 시 기존 Pages 배포 |
| 영양 DB 3종 | 매주 **월요일 05:35** · 수동 실행 가능 | 공식 전체 파일 수집 → 전수 검증 → 레시피 연결·현황 재생성 → Actions 결과물 보관 | **아니오**. 수집 결과 검토·main 반영 필요 |
| 원재료·품목·회수·HACCP·과거 바코드 7종 | **정기 일정 없음** · 수동 실행 | 서비스별 순차 수집·검증 → 격리 데이터 브랜치와 결과물 보관 | **아니오**. 별도 번호·검색 인덱스 생성 및 main 반영 필요 |
| 공식 API 검색·번호 연결 인덱스 | **정기 일정 없음** · 수동 실행 | 지정한 데이터 브랜치에서 생성·검증 후 같은 브랜치에 커밋 | **아니오**. 검증된 데이터와 함께 main 반영 필요 |

위 시각은 저장소 cron 설정 기준이다. 제공기관의 원본 갱신 주기와 우리 앱의 수집 실행 주기는 서로 다르다. 사용자가 검색할 때는 마지막으로 운영 반영된 정적 수집본을 조회하며 공공 API를 실시간 호출하지 않는다.

- 수집본 시각은 상태 파일에 기록된 `fetchedAt`이다. 기관이 각 레코드를 마지막으로 수정한 시각을 뜻하지 않는다.
- 보관 원본을 다시 변환한 경우 원래 수집본 시각을 유지하고 `reprocessedAt`을 따로 기록한다.
- 공식 전체파일의 HTTP 갱신 시각은 `sourceLastModified`에 보존한다. 이 값도 전체 개별 레코드의 최신성을 보증하지 않는다.
- 현재 6개 API 원본 재변환은 **2026-10-21 00:23:59~00:26:49 KST**에 수행됐다. 공공 API를 추가 호출하지 않았다. C005는 기존 검증 수집본을 유지했다.

전체파일과 실시간 API 참조 건수가 다른 경우 두 수를 모두 기록한다. 아래 완료는 **제공된 공식 전체파일의 모든 행을 변환·검증했다는 뜻**이며 실시간 API와 같은 스냅샷이라는 뜻이 아니다.

| 데이터 | 공식 전체파일 수집 행 | 실시간 API 참조 건수 | 파일 행 수 − API 건수 | 처리 |
| --- | ---: | ---: | ---: | --- |
| I0490 회수·판매중지 | 378 | 379 | -1 | 파일 전체 378행 검증; API와 건수 차이 표시 |

## 5. 수집 방식·파일 구조

| 구분 | 수집·변환 방식 | 보관 경로·형식 | 앱 조회 방식 |
| --- | --- | --- | --- |
| 레시피 | 인증키로 전체 API 수집, 원문·정규화·브라우저 스냅샷 생성 | `data/raw-full.json`, `data/recipes.json`, `assets/data.js` | 브라우저 레시피 데이터에서 검색 |
| 영양 3종 | 공식 전체 워크북 다운로드, 모든 원본 열·값 유지 | `data/nutrition/manifest.json`, 검색 `index.json.gz`, **1,000행** 단위 `part-*.json.gz` | Worker 검색 후 선택한 상세 분할 파일만 로드 |
| 추가 API 7종 | 첫 API 응답으로 인증·참조 총건수 확인 후 공식 전체파일 다운로드, 순차 처리 | `data/collection/{서비스}/status.json`, **10,000행** 단위 `records-*.jsonl.gz` | 원본별 검색 및 필요한 원문 분할 파일 조회 |
| 보관 원본 | 현재 6종의 공식 gzip 파일 보존. 큰 원본은 분할 보관 경로 지원 | `source-original.gz` 또는 `originalParts`에 기록된 파일 | 일반 앱 검색에는 원본 전체 다운로드 불필요 |
| 공식 API 검색 | 원문 전체 레코드의 검색 포인터 생성 | `data/food-safety/{서비스}/index.json.gz` | 사용자가 선택한 원본 하나를 Worker에서 로드 |
| 공식 번호·원료명 연결 | 품목번호·과거 바코드·업소번호·원료코드·공식 이름 조회 키 생성 | `data/food-safety/lookup/00~ff.json.gz`, **256개 버킷** | 필요한 버킷과 해당 원문 파일만 로드 |
| 수집 현황 | 실제 상태·건수·버전·연결 포인터 합계로 재생성 | `data/collection-status.json`, `data-status.html` | HTML 현황은 JavaScript 없이도 조회 가능 |

- CSV 인용부호 안의 쉼표와 gzip을 처리한다. UTF-8/UTF-16 및 필요 시 CP949 판독을 지원한다.
- 영양 기준량·제공단위량·원문 날짜·0·누락값을 보존하며 임의로 100g이나 1인분으로 환산하지 않는다.
- 추가 API 원본의 중복은 고유 행 수로 별도 집계하며 원문 행을 임의로 삭제하지 않는다.
- 현재 C005에는 검증된 전체 원문 JSONL이 있다. `source-original.gz`가 없는 기존 수집본이므로 아래 보관 원본 재변환 예시에서는 C005를 제외한다.
- `--reuse-source`는 현재 `source-original.gz`가 있는 경우에 사용한다. 분할 원본만 있는 경우에는 그대로 재사용할 수 있는 것으로 안내하지 않는다.

| 일시적 API 오류 | INFO-500·일부 HTTP 5xx·연결 오류에 최대 7회 시도; 재시도 대기 5~30초 |
| 활용신청 오류 | INFO-110은 해당 서비스 활용신청 상태 문제로 기록 |
| 정상본이 있는 API의 재수집 실패 | 마지막 정상 스냅샷 보존; `status-last-attempt.json` 및 최근 시도 상태 기록 |
| 이전 정상본이 없는 실패 | 차단·부분 수집·사유를 기록; 정상 전체 수집본으로 연결하지 않음 |
| 인증키 | GitHub Actions Secret `FOODSAFETY_API_KEY`; 브라우저·HTML·공개 JSON·문서에 키 값 저장 금지 |
| 호출 방식 | 동일 키의 추가 API는 순차 실행. 일반 앱 검색은 공공 API를 호출하지 않음 |

현재 원문 검증의 필드 검사는 API와 전체파일에 대응되는 필드가 있는지 확인하는 방식이다. 모든 필드의 의미·정확성이나 법적 유효성까지 자동 검증했다는 뜻은 아니다. 포인터 검증도 연결 대상의 품목·제조분·인증 적용 범위까지 판정하지 않는다.

## 7. 워크플로·설정 표

| 작업 | 파일·실행 링크 | 트리거 / cron(UTC) | 실행 제한 | 결과물·반영 |
| --- | --- | --- | --- | --- |
| 레시피 수집 | [Sync FoodSafety recipes](https://github.com/softm/foodhannun/actions/workflows/sync-recipes.yml) · [설정](../.github/workflows/sync-recipes.yml) | 수동 + `20 21 * * *` → KST 매일 06:20 | 동일 레시피 수집 작업 동시 실행 방지 | 검증 후 main commit/push |
| 영양 수집 | [Collect complete K-FIND nutrition DB](https://github.com/softm/foodhannun/actions/workflows/collect-nutrition.yml) · [설정](../.github/workflows/collect-nutrition.yml) | 수동 + `35 20 * * 0` → KST 월요일 05:35 | 최대 90분, 동일 작업 동시 실행 방지 | `foodhannun-complete-nutrition`, 30일 보관. main 쓰기 없음 |
| 추가 7종 수집 | [Collect additional official food data](https://github.com/softm/foodhannun/actions/workflows/collect-additional-data.yml) · [설정](../.github/workflows/collect-additional-data.yml) | **수동만**, schedule 없음 | 최대 360분, 동일 수집 작업 동시 실행 방지 | `data/foodsafety-{실행ID}-{시도번호}` 브랜치, `food-safety-complete-snapshots` 30일 보관 |
| 공식 검색·번호 인덱스 | [Build official food identifier links](https://github.com/softm/foodhannun/actions/workflows/build-foodsafety-index.yml) · [설정](../.github/workflows/build-foodsafety-index.yml) | **수동만**, schedule 없음 | 최대 90분, 같은 데이터 브랜치의 동시 작업 방지 | 입력 데이터 브랜치에 인덱스·현황 커밋. main 변경 없음 |
| 운영 배포 | [배포 이력](https://github.com/softm/foodhannun/actions) | main 브랜치 루트의 Pages 배포 | 기존 Pages 구성 사용 | 운영 사이트 정적 자료 갱신 |

Actions 결과물의 30일 보관과 저장소의 Git 이력 보관은 별개다. 영양 수집 결과물은 운영 반영하거나 별도로 보존하지 않으면 결과물 보관기간이 끝날 수 있다.

## 8. 수동 수집·운영 반영 절차

### 8.1 레시피

1. [레시피 수집](https://github.com/softm/foodhannun/actions/workflows/sync-recipes.yml)에서 **Run workflow → main**으로 실행한다.
2. Secret이 있으면 전체 수집·검증·연결·현황 재생성이 실행된다.
3. 데이터 변경 커밋과 Pages 배포 성공을 확인한다. Secret이 없으면 수집을 건너뛰므로 단순 실행 성공 표시만으로 새 데이터 수집을 판단하지 않는다.

### 8.2 영양 DB 3종

1. [영양 수집](https://github.com/softm/foodhannun/actions/workflows/collect-nutrition.yml)을 main 기준으로 실행한다.
2. `foodhannun-complete-nutrition` 결과물을 확인한다.
3. 원본 버전·건수·검증 결과를 검토한 후 영양 데이터, 음식 영양 연결 파일, 수집 현황을 함께 main에 반영한다.
4. Pages 배포 후 메인 검색·기준량·상세 원문을 확인한다. 현재 이 검토·반영은 자동화되어 있지 않다.

### 8.3 추가 7개 API를 새로 수집할 때

[추가 데이터 수집](https://github.com/softm/foodhannun/actions/workflows/collect-additional-data.yml)에서 main을 선택하고 다음처럼 실행한다.

| 입력 | 전체 새 수집 예시 | 의미 |
| --- | --- | --- |
| services | `I0490 I0580 I1020 I2520 C005 I1250 C002` | 공백으로 구분한 서비스 목록. 필요한 일부만 지정 가능 |
| source_snapshot | `main` | 기존 정상 수집본을 가져올 기준. 기존 `data/foodsafety-숫자-숫자` 브랜치도 가능 |
| reuse_source | **false** | 공식 API와 전체파일을 새로 조회 |

수집 성공 후 다음을 수행한다.

1. 생성된 `data/foodsafety-{실행ID}-{시도번호}` 브랜치의 7개 `status.json`과 최근 실패 시도를 확인한다.
2. [인덱스 생성](https://github.com/softm/foodhannun/actions/workflows/build-foodsafety-index.yml)의 `snapshot_branch`에 해당 데이터 브랜치명을 입력한다.
3. 전체 검색·번호 조회 검증 성공과 원본별 건수·날짜·API 차이를 검토한다.
4. 검증된 원문·인덱스·수집 현황을 함께 main에 반영한다. 최신 앱·수집기 코드가 예전 브랜치 코드로 되돌아가지 않게 확인한다.
5. Pages 배포 후 제품번호 연결, 회수 대상 제조분, 업소 HACCP 범위, 원료 사용 조건과 수집 현황을 확인한다.

### 8.4 API 호출 없이 보관 원본만 재변환할 때

| 입력 | 현재 원본 보유 기준 예시 |
| --- | --- |
| services | `I0490 I0580 I1020 I2520 I1250 C002` |
| source_snapshot | `main` 또는 원본이 있는 `data/foodsafety-숫자-숫자` 브랜치 |
| reuse_source | **true** |

이 작업은 **새 데이터 수집이 아니라 기존 원본의 재변환**이다. 수집본 시각을 새 데이터처럼 바꾸지 않으며, 이후 번호·검색 인덱스를 다시 생성한다. 보관 원본이 없는 서비스를 포함하면 해당 서비스의 재변환이 실패할 수 있다.

## 9. 데이터 해석·연결 원칙

| 관계 | 연결 기준 | 해석상 제한 |
| --- | --- | --- |
| 레시피 → 음식 영양 | 음식명·허용 별칭·가장 구체적인 이름 포함 후보 | 같은 레시피의 영양값으로 확정·합산하지 않음 |
| 영양 제품 → I1250·C002·I0490·과거 C005 | **정확히 같은 품목제조보고번호** | 제품명만으로 원재료·회수·바코드 확정하지 않음 |
| I1250 → I0580 | **정확히 같은 업소 인허가번호** | 업소·적용 품목·기간·취소·폐업을 확인. 제품의 현재 인증 보장 아님 |
| 레시피 재료 → I1020·I2520 | 공식 원료명·이명 일치 후보 | 사용 부위·가공·조건까지 확인. 이름만으로 코드·사용 가능 여부 확정하지 않음 |
| 제품 → 회수 공고 | 품목번호 일치 공고와 제조일·기한 원문 | 같은 제품의 모든 제조분이 회수 대상이라고 단정하지 않음. 공고 없음도 안전 보장 아님 |
| 바코드 조회 → C005 | 과거 바코드 정확 일치 | 현재 유통제품 식별·진위·재고 보장 아님 |

알레르기 성분·교차 접촉은 실제 제품 표시와 원문을 별도로 확인한다. 영양값의 100g·100ml·1인분·mg 등 서로 다른 기준을 자동 병합하지 않는다.

## 10. 개선 주기 제안 — 현재 미설정

다음은 운영 개선 제안이다. **이 문서 작성으로 cron이나 자동 반영 설정을 변경하지 않았다.** 제공기관의 공표 주기를 확인한 것으로 해석하지 않는다.

| 데이터 | 제안 주기(KST) | 필요한 추가 구현·조건 |
| --- | --- | --- |
| 레시피 | 현재 매일 06:20 유지 | 실패·오래된 수집본 상태를 운영 현황에서 확인 |
| 영양 DB 3종 | 현재 주간 월요일 05:35 유지 | 원본 버전·해시 변경 검토와 검증 후 운영 승격 절차 보완 |
| I0490 회수·판매중지 | **1시간 간격 조회 검토** | 전체파일/API 차이와 최신 공고 누락 점검, 안전 공고 갱신 지연 표시 필요 |
| I1250·C002 | 매일 04:00 전체 수집 검토 | 대용량 파일 수집·보관·용량 관리, 두 자료 기준시점 차이 검토 |
| I0580 HACCP | 매일 05:00 수집 검토 | 지정·만료·취소·폐업 필드 함께 검증 |
| I1020·I2520 | 주 1회 수집 검토 | 두 자료의 부위·조건·코드 관계 검토 |
| C005 과거 바코드 | 정기 수집 제외·기존본 보존 제안 | 새 갱신 여부가 확인되기 전까지 과거 자료 경고 유지 |

반영이 필요한 핵심 과제는 추가 API의 정기 수집 설정, 검증된 원문·인덱스의 동시 운영 승격, 그리고 마지막 정상 수집 시각과 최근 실패 시도의 구분이다. 현재 이 세 기능을 모두 자동화한 상태로 안내하지 않는다.
